## Findings

### B1 — P2: read-only recovered consumer still admits new mutations, then strands selection

Locations: `studio/host/core/fixture_selector.py:526–550` (`prepare`), `575–616` (`stage`/`select`), `365–388` (file adoption), `773–777` (restore); `studio/host/core/safe_replace.py:172–176` (read-only gate).

After a successful commit, read-only reopen and successful `load_committed`, `prepare` has no admission check for the consumer's permanent write hold. It returns ACCEPTED_PENDING; stage writes a new release and select advances the durable selection. Only adoption discovers `SAFE_REOPEN_REQUIRES_RECONCILIATION`. That leaves UNKNOWN and `ready=false` despite an intact previously verified active file. Explicit restore appends another selection and also fails on the same read-only hold, leaving RESTORING. No current API can finish that write, so ordinary new work can turn a readable recovered state into avoidable unresolved work.

This was reproduced without mocked filesystem failures. Actual file identity and bytes stayed unchanged: the write protection works. The defect is late admission and avoidable state progression, not an unauthorized overwrite.

Reproduction, run from `studio` in a 35-second owned runner (imports the existing disposable fixture helper):

```python

sys.path.insert(0, 'tests/protocol')
from test_file_consumer import FileConsumerTests
x = FileConsumerTests(); x.setUp()
try:
    x.activate(x.request())
    x.reopen()
    x.selector.load_committed(now_ms=201)
    before = x.files.read('active.json')
    request = x.request('after-restart', 'two')
    x.selector.prepare(request, now_ms=202)  # ACCEPTED_PENDING
    x.selector.stage('after-restart', now_ms=203)
    x.selector.select('after-restart', now_ms=204)
    x.selector.adopt('after-restart', now_ms=205)  # ADOPTION_UNKNOWN
finally:
    x.doCleanups()
```

### B2 — P1 acceptance gap: acknowledged receipt/high-water custody does not survive independently

Locations: `studio/host/core/private_events.py:55–59,96–100,244–259,338–339`; `studio/tests/protocol/test_file_consumer.py:178,207–211` (test witness printed before exit); `studio/host/core/PRIVATE_EVENTS.md` and `FIXTURE_SELECTOR.md` explicitly retain the custody gap.

`EventBinding` is a trusted caller-supplied root/stream/high-water value. The implementation updates its witness in memory and can reject a suffix older than that witness; it does not durably maintain custody of the latest acknowledged head/root bindings outside the state whose loss must be detected. The crash fixture transports the fresh binding through stdout to its surviving parent, which is valid test scaffolding but not a production restart/custody protocol.

A controlled whole-frame suffix-loss probe confirmed the exact limit. Save witness at sequence 1, append/ack sequence 2, close, truncate `.events` in place to the saved sequence-1 byte length, then reopen. The stale trusted witness permits reopening at sequence 1. Supplying the current sequence-2 witness correctly returns `EVENT_RECOVERY_REQUIRED`, outcome unknown. This is a fault-model probe under trusted test control, not an AppContainer access bypass and not a claim that NTFS spontaneously lost a flushed record.

```text
STALE_WITNESS latest_sequence=2 reopened_sequence=1 old_witness_accepted=true
CURRENT_WITNESS_REJECT code=EVENT_RECOVERY_REQUIRED unknown=true
```

Fix: implement and test the broker's durable root/stream/receipt/high-water custody protocol with explicit commit ordering, missing-state refusal and current-head rollback detection. Include restart after acknowledged COMMITTED/STOP and loss/rollback of an entire valid suffix; do not provision a fresh empty selector when custody is missing. Until then the journal/readback tests cannot establish complete crash/retry custody or justify the public mutation gate.
