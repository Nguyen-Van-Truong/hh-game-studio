Final run `GT02-S33-IPC-05` completed both native cases. A primary AppContainer
process sent fixed bounded bytes through a local named pipe; the broker checked
the client PID against its retained live process, inspected the pipe client's
AppContainer token/SID, reverted impersonation, and called the actual
`PrivateBlobStore.put_bytes` from S32. The broker read back the staged blob.
The worker could neither read nor write that blob directly (access denied5).

A second case deliberately gave the broker an incorrect expected PID. The
same type of client connected, but identity binding rejected it and the blob
count stayed unchanged. This tests a wrong broker binding, not PID recycling,
cross-session spoofing or another package's client. Both native processes exited
53 with completion markers; final Job active count0 and PID lists empty.

The server uses one first-instance pipe, remote-client rejection, noninheritable
handles, bounded frames (128 input bytes), overlapped I/O with timeouts and a
protected explicit DACL/Low label. The client grant `0x12019b` excludes the
FILE_CREATE_PIPE_INSTANCE bit. Effective pipe security is read back. A positive
connection does not grant the client access to the filesystem or store handles.
The typed production envelope, journal, lease/fencing and reserved Stop path
are not integrated into this fixed diagnostic protocol.

All file/IPC/profile operations were limited to owned synthetic fixtures. The
unique profile was absent before, present after creation, then absent in both
package directory and registry mapping after deletion. Both profile HRESULTs
were0. The native processes use detached suspended launch, child-process
restriction, a one-process Job cap and128 MiB memory cap. The owned TEMP was
removed after handles/processes closed. Earlier S30 denied cleanup was untouched.

The SID namespace choice was researched in Chromium's primary implementation
at commit `04d774d3827c8532b1b7d3966629f9193a35dd0e` after web retrieval errors;
the pinned source was retrieved directly over HTTPS. Its GetPipePath builds
the package-SID pipe namespace. This is a measured choice for the tested
Windows build, not a universal claim about UWP/desktop IPC compatibility.
[Chromium source](https://github.com/chromium/chromium/blob/04d774d3827c8532b1b7d3966629f9193a35dd0e/sandbox/win/src/app_container_base.cc).

impersonation. [Pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights),
