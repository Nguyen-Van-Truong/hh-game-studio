# S48 generated-script validation attribution — bounded design review

AUTHORITY=0. Date: 2026-09-17. Read-only source research; no Godot/container launch, test run, addon change, acceptance signature, commit or tick. This is a proposed partial validator, not implemented/proven validation and not GT-03 PASS. Requirement 2.3 remains unchanged: allowlisted bounded script edits, staged sandbox parse/import accounting for `@tool`/import hooks, syntax/type/import rejection before activation, and correct script-hash readback before ACK. It does **not** explicitly promise acceptance of every GDScript program. Whether the declarative profile below is sufficient initial availability is a later coordinator/independent-critic decision against the complete DoD, TQ03 and TX17; this report changes no accepted marker.

**Finding:** containment and a clean process exit do not authenticate completion of required engine checks. The smallest practical stock-Godot path identified here requires a deliberately restricted, explicitly named input profile. Arbitrary generated scripts remain noneligible until a stronger validation/attribution design is implemented and tested.

## What the pinned engine actually does

* The CLI documentation describes `--check-only` as a script error check, and `--import` as an editor import followed by quitting. These descriptions promise neither a security boundary nor authenticated postconditions. [Official CLI documentation](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html#command-line-reference).
* `Main::start()` loads the supplied script with `ResourceLoader::load()` **before** its `check_only` branch consults native `is_valid()`. Recovery mode requires editor mode; it also changes whether the requested scene opens. Thus neither flag combination is an equivalent scene-reopen proof. [main.cpp, lines 2109–2116, 4061–4066, 4399–4404](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/main/main.cpp#L4061).
* Script reload parses, analyzes and compiles, then calls `_static_init()` when scripting is enabled **or** the parsed script is a tool script. That gate has no recovery-mode test; the separate `can_instantiate()` gate does. The current executor's standalone parse invocation therefore can execute static initialization, even without `@tool`. A source-level counterexample is a valid `extends Node3D` script whose `static func _static_init() -> void` prints a forged marker or loops. This is source-derived, not executed here. [gdscript.cpp, lines 238–240, 622–637, 751–823](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/modules/gdscript/gdscript.cpp#L790).
* Editor construction disables ordinary scripting but explicitly retains tool execution. Merely moving the check into an EditorPlugin is insufficient. [editor_node.cpp, lines 7730–7731](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/editor/editor_node.cpp#L7730).
* The native `GDScriptLanguage::validate()` uses parser/analyzer without directly compiling the target. It is a C++ virtual, not an established callable addon API in this review. More importantly, analyzer preload handling can load resources, so it is not automatically a dependency-free, execution-free solution. [gdscript_editor.cpp, lines 134–140](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/modules/gdscript/gdscript_editor.cpp#L134), [script_language.h, line 256](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/core/object/script_language.h#L256), [gdscript_analyzer.cpp, lines 4398–4432](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/modules/gdscript/gdscript_analyzer.cpp#L4398).

The existing `forged_success` fixture concretely prints `HH_ENGINE_VALIDATED` with PASS/public-ACK fields from `_enter_tree()`, then calls `get_tree().quit(0)`. `SceneTree::quit()` sets the OS exit code and requests termination. It does not certify any validator work. [scene_tree.cpp, lines 824–828](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/main/scene_tree.cpp#L824). Its current expected outcome, `untrusted_marker`, correctly exercises a diagnostic rejection of authority; this review makes no claim about the ongoing actual run.

A trusted outer process can attest which immutable bytes/binary it launched, exit/timeout/caps, stream completeness and cleanup. It cannot infer internal semantic checks from an adversary-controlled stdout record. A new marker, child-writable result file, nonce, or credential available to the same executing script does not repair that distinction. Loading a candidate before a trusted bootstrap's report is also too late if loading runs candidate initialization.

## Smallest proposed fail-closed path

1. **Admit a closed profile before engine access.** For an initial supported fixture, accept whole-file canonical grammar only: `extends Node3D` and a bounded list of approved typed `@export var` declarations with finite numeric/bool literals and fixed allowed names. Validate every byte; reject extra syntax instead of stripping it. No functions, setters/getters, static data/init, nested classes, `@tool`, `preload`, script inheritance or arbitrary expressions. This is intentionally much narrower than normal GDScript. An unsupported script receives `UNSUPPORTED_PROFILE`, never validation PASS. A keyword blacklist or “remove @tool then validate” is not this profile and changes the submitted program.
2. **Close the entire load graph.** Use a host-owned fixed project configuration, no autoloads/plugins/extensions/custom importers, a fresh private cache, and a canonical bounded scene containing only approved native node/resource types and the one admitted script reference. Reject extra scene resources, embedded scripts, inheritance, connections and unexpected files before Godot loads them. Bind scene, script, configuration, trusted bootstrap, engine and all UID/source dependencies in one immutable validation manifest. The current two-content bundle omits `.gd.uid`/configuration/trusted-addon metadata; it is not this complete closure.
3. **Run the real stages under the bounded executor.** Keep separate pinned `--check-only` and editor import stages, then a fresh trusted bootstrap process. The bootstrap loads the original admitted bytes, requires `Script.reload(false) == OK`, checks the native base type and script hash, and inspects `PackedScene.get_state()` for the exact hierarchy, attached script and stored properties. The public APIs exist; native `Script.is_valid()` is not the addon API to assume. [Script bindings](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/core/object/script_language.cpp#L151), [PackedScene state API](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/PackedScene.xml#L80), [SceneState property API](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/SceneState.xml#L148). For actual instance/export readback, instantiate only this admitted profile and compare its values before freeing it. SceneState inspection alone is not instance readback. The profile prevents candidate callbacks; the bootstrap must never invoke arbitrary candidate methods.
4. **Let the host own the decision.** Bind bootstrap completion to the exact job, expected hashes and manifest. Require real zero exits, no parse/type/import diagnostics, timeout or cap event, complete EOF on every reader, no reader/host/evidence-write error, unchanged input/toolchain, and owned-process/container cleanup. Missing, duplicate or conflicting completion is failure/UNKNOWN, even with exit zero. The report's credibility rests on preventing submitted code from executing in the reporting process, not on the marker format. Recheck the active immutable revision through the future durable publication owner before any public COMMITTED receipt; neither this design nor the pure reducer supplies that owner.

This path is a useful, testable **partial profile** that could expose real bounded text changes after actual sandbox parse/import and cross-readback. It does not establish validation of arbitrary functions, `@tool` or import hooks; those inputs must be visibly unsupported. No reviewed stock CLI primitive establishes their general attribution boundary. This is an availability proposal, not a claim that arbitrary-language support is intrinsically necessary for GT-03, nor a declaration that the profile already fulfills its complete DoD. Future trusted controller scripts can be separately pinned source; they must not silently become candidate-controlled validator code. Broader validation/reporting needs a separate bounded proof; a fork/module/GDExtension is not authorized by this report. Sandbox containment remains independently required, including hard disk limits and cleanup; it cannot be waived because input eligibility is narrower.

## Required proof before enabling even the partial profile

Positive: exact admitted script, actual parse/import, fresh scene/resource load plus instance/export/hash readback, and host-bound completion. Negative: existing forged marker/quit fixture; non-tool `_static_init`; static initializer in a dependency; embedded scene script; preload/resource hook; syntax/type error; scene/script mismatch; same candidate under changed config/UID/bootstrap/binary; unexpected grammar byte; exit zero before completion; duplicate/replayed completion; truncated/erroring pipe; deadline/output/disk cap; Stop at each stage. Every unsupported executable feature must fail before launch, and every incomplete stage must prohibit activation. These are proposed tests, not tests run by this review.
