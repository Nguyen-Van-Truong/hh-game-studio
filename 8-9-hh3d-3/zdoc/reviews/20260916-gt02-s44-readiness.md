## Decision

S44 is a useful internal foundation, but public safe-write is not ready. The shortest sound path is to finish a **single-project, fixed-file protected publication owner** around the existing selector, give it durable restart custody, then expose the existing typed fixture operation with truthful scopes. Do not build a general filesystem service or wait for a Godot/Blender consumer.

The next coding task should be **terminal-state restart custody and mutation rearm**, with public capabilities still disabled during that task. It should prove: commit revision A; terminate the owning process; reopen using only broker-owned durable state; verify A; accept new revision B exactly once; return A/B's original receipts on retries. This directly closes the current practical discontinuity. Public registration and adversarial IPC remint form the next bounded task after that contract works.

The tools plan is explicit: GT02's S30 clarification at lines 582–585 says safe `UNSUPPORTED` does not remove the TX15 availability GAP. Keeping the global mutation flags false is correct today; it is not sufficient to tick GT02. Conversely, GT02 BUILD explicitly permits a mock operation fixture. Actual Godot editor mutation is GT03, Blender is GT04, and cross-application recovery is GT07.

## Concrete architecture fitting the existing modules

### Ownership and public boundary

Add a small trusted owner under `studio/host/core`, for example `ManagedFixtureHost`. It owns one project's provision binding, custody, event log, blob store, `ProtectedFileRoot`, `FileFixtureReleaseConsumer`, `FixtureSelector`, `SelectorFixtureBroker` and endpoint/pump lifetimes. Reuse the existing primitives; do not introduce a second transaction reducer or wrap the same effect in both `Journal` and `PrivateEventLog` with competing command authority.

Local API shape:

```text
ManagedFixtureHost.create(trusted_parent, project_id, initial_revisions)
ManagedFixtureHost.open(trusted_provision_binding) -> held/read-only host
host.inspect_recovery() -> bounded state/next-action description
host.reconcile_verified_terminal() -> local verified readiness, never a wire flag
host.lookup(command_id) -> original receipt or UNKNOWN
host.close() -> stops admission, joins owned pump/endpoint, releases resources
```

The actual names are implementation choices; the ownership and ordering are requirements. Initial roots and identities are persisted before any externally visible admission. Reopen uses existing exact names/identities and never mints replacement stores because something is missing. Keep the file namespace in its dedicated parent so peer ancestor sharing does not block its directory barrier.

Clients retain the current strict `fixture.release.activate` request, fixed `{"stable_id":"active-release"}`, inert asset grammar, 8192-byte canonical payload cap, expected revisions, parent generation/hash, command ID, deadline and lease/fence. They receive bytes, revisions, hashes and receipts; never a root path, OS handle, DACL, native flag, consumer object, callback, clock, witness, file identity authority or recovery policy. The broker derives `active.json` and native `FileVersion` itself.

### Durable custody, without an unbounded storage project

Recommended bounded design: **one protected nonvolatile Windows registry record as the anchor and high-water custody; the existing private event log remains the command history**. A second file/event root still needs an externally trusted identity at startup and does not solve the bootstrap problem alone. Keep this Windows backend behind a narrow local custody interface so later platform work can provide its own equivalent.

Use a fixed product-owned base such as `HKCU\Software\HHStudio\ManagedFixture\v1`, with a project leaf selected by a **locally provisioned** UUID. Public project IDs map to already-provisioned local configuration; no wire field selects a registry path. The anchor is the fixed OS registry namespace plus the trusted broker's user SID and validated protected DACL, not a file authenticating its own identity. Use a consistent registry view (the 64-bit view for this target), refuse impersonating threads, noninheritable handles and no package/ALL APPLICATION PACKAGES grants. Read back owner/DACL on create and reopen; do not trust an arbitrary existing permissive key, follow a client-selected registry path or repair ACLs in place to adopt unknown state. Add native AppContainer read/write/delete/create-subkey denial and positive-control tests for the exact key arrangement before counting it as the boundary.

`RegCreateKeyExW` supports a supplied security descriptor and `REG_OPTION_NON_VOLATILE`; its disposition distinguishes newly created and already existing keys. Provisioning requires the newly-created disposition. Existing projects use `RegOpenKeyExW`, never a create-on-missing fallback. A nonvolatile key persists over restart. [RegCreateKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regcreatekeyexw) Owner/DACL inspection and explicit access masks are supported for registry keys. [Registry key security](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights)

Keep one `REG_BINARY` value, for example `State`, bounded to 16 KiB with a strict canonical schema and checksum. It contains: format/version; local provision UUID/public project binding; `PROVISIONING` or `READY`; trusted configured parent locations plus exact minted root names and log root/stream, blob root and file-root identities; witnessed `EventHead` (sequence/hash/size); committed selection and terminal receipt pointer/digest; committed file identity+size+SHA256; custody generation and recovery epoch. Do not duplicate all receipts in the registry: the event stream already owns them. A single bounded value avoids a mixed-generation collection of separately updated registry values. Its checksum detects malformed/torn data, not malicious rewriting by an authorized broker/admin; do not claim it supplies authentication or undocumented atomicity.

Provisioning sequence is concrete: create the protected project leaf; persist and flush `PROVISIONING`; create/register each native resource immediately for cleanup; write `READY` with all actual identities and the initialized selector head; flush and read back; only then open worker admission. Existing/failed/incomplete provisioning never silently becomes an empty project. Failure may preserve owned orphans, which is safer than treating them as a fresh state. Startup is local `open(project_binding)`: open the existing fixed leaf, validate security/value/format, issue a fresh successful registry barrier, acquire the existing stores' exclusive guards, reread the anchor under ownership, then reopen using those saved identities/witness. Never enumerate data roots and accept whichever looks newest.

For every custody update: compare the expected custody generation under the host mutex and existing store guards; `RegSetValueExW(State)`; checked `RegFlushKey`; bounded exact `RegQueryValueExW` readback and semantic validation; only then treat that generation as witnessed. A readable registry value before a successful flush is not enough. Microsoft documents that `RegFlushKey` returns after the hive data reaches the registry store on disk; it is expensive and can block modifications across that hive. Keep synchronous custody I/O off the responsive control path and inside the owned bounded broker process, and measure the actual cost. Do not flush a hot telemetry counter. [RegFlushKey](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regflushkey)

The custody writer stays separate from worker IPC and subordinate to the same single host owner. The root trust ends at this protected OS key under the documented broker-versus-AppContainer boundary; there is no need to add another journal to witness it. A rollback of the protected registry **and** all file stores by the trusted owner/admin, or a physical storage failure violating completed flush assumptions, is not detectable by another same-disk checksum. Do not claim otherwise or add TPM/cloud/distributed consensus requirements to GT02.

Required ordering:

1. Append/flush/read back the selector event using its expected head.
2. Persist/flush/read back the corresponding custody watermark **before exposing that event as an external ACK/result or using it to authorize the next side effect**. This applies to admission, relevant effect-admission state, Stop, and terminal receipt, not just successful commits.
3. On restart, validate the anchored identities and custody first, then open the event stream using its witnessed prefix. A stream behind custody is corruption/recovery-required. Missing key/value, `PROVISIONING`, wrong type/schema/checksum, impossible epoch, identity substitution or a custody generation below the current live owner's floor also holds admission. A valid older custody value with a newer valid event stream remains held as observed unacknowledged history: explicit reconciliation may advance custody only after semantic/file postconditions pass. Never pick an older backup value because the newest one is malformed, drop the event suffix or assume its command was unexecuted. If both protected custody and history are externally restored to the same old state, that is the explicitly excluded coordinated rollback case, not something this design claims to detect.
4. For success: file flush + file readback + namespace barrier -> selector terminal append/barrier -> custody barrier -> public COMMITTED. Custody failure after a visible effect/terminal means UNKNOWN and admission hold. Every lookup path returning that terminal must also respect the custody barrier; fixing only submit leaves an ACK bypass.

Persist reservations before admission for all remaining selector records, including the terminal and Stop; prove the fixed custody record fits its cap for every reachable phase before admitting the command. A capacity refusal before any new command effect can be a no-effect rejection. A write/flush/close uncertainty cannot be converted into rejection by its error code.

### Narrow recovery and rearm

Keep ordinary `ProtectedFileRoot.reopen_readonly()` unchanged. Add only an internal transition invoked by the trusted host after reconciliation, bound to the same live root/guard, selector head, consumer binding, observed `FileVersion` and current recovery/fencing epoch. It can be a non-serializable local token consumed once or a private host-owned method under the relevant mutexes. Either way, do not publish a boolean that clears `_readonly` or `_poisoned` from caller input. Recheck the proof's head/version/Stop/fence at use so a stale proof cannot authorize a later write.

Minimum support for the next task:

| Reopened condition | Required behavior |
| --- | --- |
| No pending command; selected equals last durably adopted terminal state; exact known active file; barriers and custody pass | Bind the consumer to the verified actual file version, persist a rearm/recovery epoch, then permit a **new** command ID under a fresh lease. Prior commands remain terminal. |
| SELECTED; actual file already equals the complete selected snapshot; terminal missing | Confirm file+directory barrier, append original command terminal once, advance custody, return original semantic result without replacing again. Existing identical-byte recovery is the basis. |
| STOP persisted/requested | Keep held. Reconnect, a new session or fresh lease does not clear Stop. No automatic replay. |
| SELECTED but old file remains; partial stage; unknown/mismatched file; altered root; bad/torn/missing custody | Preserve bytes and return UNKNOWN/RECOVERY_REQUIRED with a bounded next-action description. No blind replace, restore or new root. |

The last row does not need an automatic repair engine to establish the GT02 baseline. Explicit full restoration, manual-edit merging and completion of every cross-app crash phase belong to the later gates. If this implementation elects to resolve an old-file pending selection, it must be a separately specified explicit transaction checked against the journal's exact old version, not an incidental unlock. Never infer “safe to retry” from the absence of a receipt.

Abandoned `.hh-stage-*` files are another reason to hold rather than silently clean. `safe_replace.py:_quota()` currently rejects reserved dot names. The first task can retain that conservative result. Automatic orphan deletion or repair is not needed to demonstrate clean terminal reopen + new revision.

### Public registration after custody/rearm

Use the existing `Capability` shape: operation, read scopes, write scopes and numeric limits. Advertise `fixture.release.activate` only for a provisioned, verified, writable protected NTFS host and a session with its write scope. Add inspect/lookup/Stop behavior and the minimal typed client for that same path. Discovery should report read-only/recovery-required behavior after restart until the trusted owner completes its explicit verification.

Do not flip generic `safe_open.capabilities()` to true just because Windows exists. That API still describes arbitrary project-root mutation, which this implementation does not support. Instead, document and test a precise operation scope such as `fixture.active_snapshot`: safe creation and atomic replacement of the broker-managed snapshot. The plan already permits private staged roots and GT02 mock operations. This is a truthful scoped capability, not a waiver of safe-write: real create, replace, readback, retries and recovery barriers must execute through that advertised path. General writes into a user-editable shared folder remain unsupported and cannot be counted as provided.

## Checked Windows contract limits

Microsoft's rename structure permits POSIX replacement while old target handles remain valid, and its fields contain no expected target FileID. Therefore the current protected namespace + retained identity + single writer is the actual CAS argument; switching rename flags cannot make an adversary-writable directory safe. [FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information)

Microsoft documents `FlushFileBuffers` as a checked flush with write-access requirements. This supports retaining explicit success/failure barriers; reading cached bytes does not replace a successful barrier. The cited page is not a proof of this product's complete directory transaction or physical power-loss behavior. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)

AppContainer file access follows the rights actually granted to that contained application. Public file operations must keep the broker's private roots inaccessible to the worker and authenticate the bound worker; sharing modes and random names alone do not establish that boundary. [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)
