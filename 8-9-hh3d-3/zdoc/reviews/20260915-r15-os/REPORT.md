# GT-01 OS/VPS failure research and validation map

Date: 2026-09-15  
Scope: rare operating-system, process, filesystem, headless-rendering and Android-host failures that can invalidate GT-01 evidence or make later GT-04/GT-06/GT-08 jobs unreliable.

This is a read-only research report. It does not change source files, plan checkboxes, pins, or acceptance status. Recommendations below are validation gates to add to the existing rows; they are not evidence that a gate has passed.

## Decisions supported by primary documentation

1. **Use an owned process handle/job or cgroup as the authority, never a bare PID.** Windows documents that a process identifier is valid only until termination and that handles remain valid after termination; a PID can therefore be recycled after a monitor loses the process. `AssignProcessToJobObject` can fail when the process is already in a job or the job is terminating, and the process may be terminated when an active-process or time limit is exceeded. [1][2][3]
2. **Treat process-tree attachment as a race with explicit outcomes.** Windows child processes normally inherit a job, but breakaway flags and nested-job ordering can leave descendants outside the observed tree. Linux process groups/sessions provide a portable fallback; `setsid()` creates a new session and group, and `kill()` with a negative PID addresses a process group. [1][4][5]
3. **Use Unicode APIs and capability checks for paths; test short and long roots.** Win32 has a 260-character default, while long-path behavior requires both the `LongPathsEnabled` policy and an application manifest declaration. The `\\?\\` form rejects relative paths and performs minimal path normalization. The shell may still fail to interpret paths that the API accepts. [6]
4. **Atomic replace is conditional, and durability is a separate step.** Python documents that `os.replace()` is atomic on POSIX only when source and destination are on the same filesystem; Windows replacement has different existence semantics. Linux `fsync()` can report `ENOSPC` or `EDQUOT`, including delayed allocation failures. A successful rename or process exit is not proof that bytes are durable. [7][8]
5. **Headless Godot is valid only when the command and renderer are recorded.** Godot documents `--headless`/`--display-driver headless` for environments without a display or GPU, and its command-line parser does not warn for an argument unsupported by a particular build. A headless PASS therefore requires pinned binary/version, exact arguments, parsed output and real host exit. [9][10]
6. **Blender background mode removes UI/audio assumptions but does not make Python thread-safe.** Blender supports `-b/--background`, `--factory-startup`, `--python-exit-code`, and explicit GPU backends. Blender's API guidance warns that Python threads can crash or corrupt data; multiprocessing or an external process is the safer boundary. Godot's `.blend` importer itself launches Blender and is unavailable in Android/Web editors, so GLB remains the portable release boundary. [11][12][13]
7. **Android emulator acceleration is conditional and can produce false confidence.** Android recommends `-gpu auto` by default, permits host/software fallbacks, and warns unsupported GPU modes may crash or render incorrectly. VM acceleration requires compatible CPU virtualization and cannot run reliably inside another VM; CI headless emulators can hide visible/interactive defects. A physical-device run remains necessary for GPU/UI acceptance. [14][15]

## Recommended additions to existing gates

### GT-01

- Add an `OS_IDENTITY` evidence object containing platform, kernel/build, filesystem, process identity method, renderer/headless arguments, and resource-limit state. Redact usernames, absolute host paths, tokens and raw environment values.
- Require a **negative test** for each platform: PID reuse simulation, failed Job Object assignment, process breakaway, Linux session escape, long-path/reparse rejection, disk-full/EDQUOT and unsupported headless flag. Negative tests must show the expected typed error and leave no owned process or partial active manifest.
- Keep `SKIP_ENVIRONMENT` for unavailable VPS capabilities, but include the remediation command and do not promote the run to acceptance.

### GT-04 / GT-05

- Pin Blender executable and exporter version, use `--factory-startup`, set a run-local configuration directory, and set Blender's Python exit-code option. Treat warnings from implicit startup data, missing libraries, GPU backends or external textures as explicit failure causes.
- Make GLB the CI/mobile artifact. `.blend` import can remain an opt-in desktop convenience because Godot documents that it calls an external Blender process and is unavailable in Android/Web editors. [12][13]

### GT-06 / GT-08

- Separate three claims: deterministic headless simulation, windowed desktop UX, and physical Android rendering/input. Each requires its own command, source hash and postcondition; passing one cannot stand in for another.
- Record Android `-accel-check`, `-gpu` mode and physical-device inventory. Emulator results are ABI/page-size/install evidence only, as the existing plan requires.

### GT-07 / GT-10

- Store cgroup/job/process-group identity in the journal and make cleanup idempotent. A restart must reconcile `PREPARED`, `VALIDATED`, `ACTIVATING` and `COMMITTED` states using hashes, not exit code alone.
- For activation, stage on the destination filesystem, flush, replace, reopen and hash. If free-space or quota checks fail, retain last-good state and emit a machine-readable recovery reason.

## Operational runbook for a failed VPS run

1. Preserve the run directory and hashes; do not delete partial evidence while diagnosing.
2. Read the independently captured host exit, signal/exception, stderr and process-tree snapshot. If any is missing, classify `UNVERIFIED`.
3. Check Windows Job Object assignment/limit events or Linux `cgroup.events`, `memory.events`, `pids.events`, and systemd/OOM records.
4. Check free bytes and quota on the source, temp, log and destination filesystems. Verify temp and destination have the same device/volume before retrying atomic replace.
5. Verify executable/version/hash and exact command flags; do not infer headless mode from a banner.
6. Retry once in a fresh unique run directory after remediation. Reuse of a run ID/source hash is forbidden after any source or environment change.

## Limitations and confidence

The cited documents specify API semantics and operational constraints; they do not prove that every Godot, Blender, VPS image or hypervisor combination behaves identically. Kernel versions, filesystem drivers, endpoint security, nested virtualization and cloud quotas can add failure modes. Therefore the plan's fail-closed evidence rules and per-environment inventory remain necessary. No claim here changes GT-01's current `IN_PROGRESS` status or authorizes a checkbox tick.
