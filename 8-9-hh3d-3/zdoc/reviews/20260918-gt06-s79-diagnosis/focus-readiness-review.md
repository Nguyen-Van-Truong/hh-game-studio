# S79 focus readiness — preimplementation review

2026-09-18, Asia/Saigon. Read-only review of the S79 object-owner hypothesis, causal-probe draft, current benchmark producer/validators and relevant plan constraints. Only this report was written. No engine/test was run, no runtime source was edited, and no acceptance/critic verdict is given. HEAD observed near completion: `e4bbc1fe3a99d5860fb0c5ca9e163860b05f4d2a`; coordinator activity is independent of this lane. Godot scope is official pin `ed1daf0bf001b61586d9930840f2f1394092c079`.

**Recommendation, conditional on the coordinator's causal probe:** use one explicitly synthetic application-focus-in notification as a fixed, recorded startup setup operation after the approved fixture/adapter are ready, before the existing startup settling interval and before batch 0. Do not implement this merely because +4 is plausible. First require the probe to show the predicted same-process root allocation/replacement behavior without file/scene drift or errors. This does not establish the cause of the historical S78 failure by itself.

Keep the change in the disposable benchmark driver. Do not change accepted production adapters, pin, thresholds, warmup count, workload mix, deadlines or memory baseline. Do not copy the diagnostic's full private-Tree scanner into the benchmark or mutate TreeItems directly.

| Approach | What it establishes | Risk / limitation |
|---|---|---|
| `get_window().grab_focus()` plus bounded observation | A real window-focus request, followed by independently observed application-focus notification and completed postconditions, can establish a real OS focus transition. | The call returns no success result. In this pin it reaches the display-server foreground request; Windows calls `SetForegroundWindow`, while duplicate application-focus state is ignored. An already-focused editor may emit no new application-focus event, so `has_focus()==true` or a returned call is insufficient to establish late-created editor handlers ran. Forcing an out/in edge adds desktop coordination and focus-loss side effects. |
| `get_tree().root.propagate_notification(NOTIFICATION_APPLICATION_FOCUS_IN)` once, explicitly labeled synthetic | Deterministically invokes the Node notification path after the relevant editor nodes exist, independent of OS foreground state; the probe can read back the specific Tree effects. | It does not establish real OS focus, user input delivery or DisplayServer application state. It broadcasts to all nodes, not only the two hypothesized owners; external-change scanning and deferred extension reloads must settle and source/fixture state must remain unchanged. |

The foreground behavior above follows [pinned Window implementation](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/main/window.cpp#L2218) and [pinned Windows foreground/application-event handling](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/platform/windows/display_server_windows.cpp#L2890). Notification propagation recursively calls Node notification handlers; it is not an OS event injector. [Pinned Node API](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/Node.xml#L807).

No silent real-focus-first/synthetic-fallback policy: that would give fresh runs different setup paths. If the coordinator selects a real-focus protocol instead, freeze that protocol explicitly, require an observed application-focus edge and later runtime postcondition, and fail within the existing timeout when the OS does not provide it. Do not add clicks, minimize/restore loops or another application merely to manufacture the edge.

## Why the insertion point is before the existing settle

`studio/tests/replay/benchmark_native.gd::_initialize()` (line 303) already waits for the accepted adapter, checks inactive IPC and the approved scene, stores `_baseline_revision`, and waits four process frames plus 1,100,000 microseconds before `_begin_batch()`. The one-shot setup fits after the initial valid snapshot/root checks and before `_startup_settle_frame`/`_startup_settle_us` are recorded. Capture the original revision and relevant file hashes before dispatch; start the existing settling clock after return. Do not re-enter dispatch on later process ticks.

The editor handler also calls filesystem scanning and schedules extension reloads; the script-editor handler checks on-disk script state. These are wider effects than creating empty roots. [Pinned EditorNode handler](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/editor/editor_node.cpp#L966), [pinned ScriptEditor handler](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/editor/script/script_editor_plugin.cpp#L1445). Use the public filesystem scan-state readback if needed to prevent readiness during a scan; retain the existing phase deadline instead of waiting indefinitely. [Pinned EditorFileSystem API](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/EditorFileSystem.xml).

At settled readiness, require the same approved root/generation/revision and unchanged fixture/source file hashes; no active filesystem scan, held operation, warning or error. Keep primitive counters/timestamps and bounded dictionaries only; avoid new persistent Nodes, Timers, Resources or retained diagnostic objects that would themselves affect ObjectDB. The startup receipt claims notification delivery and settled fixture state, not per-run proof that exactly four objects were added or that OS focus occurred.

## Falsifiable prerequisite and verification

The coordinator's current probe draft already labels its propagation stimulus as synthetic and observes same-run owner callbacks, root IDs, file state and pre/post counters. Before adopting setup, it must show: any initially null candidate roots become blank roots in the identified same-PID owners; a subsequent notification replaces old root identities without accumulating another retained step; old roots are invalid, file/scene state remains unchanged, and the settled observations are clean. Two roots plus a +4 total is consistent with the private TextParagraph explanation; it does not individually identify the two private paragraphs. A missing/ambiguous owner, unexpected children/dialog, accumulating second step, drift or error falsifies the proposed narrow explanation.

A clean causal probe still does not prove an actual OS event caused S78. Preserve that uncertainty. A bounded real-focus observation is useful for the OS path but must not be claimed from synthetic notification records. Likewise, readiness setup does not replace GT-06's independent real-input/no-focus-input evidence.

After implementation, run only the focused validator cases and the changed native readiness path first, then freeze the changed source closure and remint the required benchmark. Keep **10 fresh host/editor pairs, each 35 batches = 5 warmup + 30 measured; each batch 1000 host commands + 100 native cycles; baseline exactly batch 4**. Preserve 15-second native phase, 20-second host READY and 7410-second native run limits, heartbeat coverage, joint/ACK order, RSS bound, raw objects/resources/handles and actual exit/cleanup proof. Do not reset/subtract counters, exempt +4, move the baseline, add warmup iterations or combine partial attempts. If later focus still raises measured counters, the run fails under the existing rule and this setup is insufficient.
