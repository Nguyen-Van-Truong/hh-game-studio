# S74 Windows memory research — supplemental diagnosis

Prepared 2026-09-18, Asia/Saigon. Scope: primary Microsoft/Godot research and a proposed bounded diagnostic. This is not a critic verdict, benchmark acceptance, or permission to alter the RSS/deadline gates. No engine, test, process-control command, setting change, or source edit was performed for this report.

The defensible next step is a small, separately owned touch/idle/wake probe, followed by readback of the actual campaign launch policy. Windows documentation supports residency churn as a possible explanation, but does not prove that trimming caused the S73 failure or supply an innocuous per-process switch that guarantees residency. Preserve the failed campaign and both failure conditions.

Coordinator-supplied observations after termination: no exact-name match among MemReduct, MemPlus, RAMMap, EmptyStandbyList, ISLC, CleanMem, Mini_Monitor, WiseMemoryOptimizer, ProcessLasso, or ProcessGovernor; WPR reported not recording. System committed bytes were 49,851,535,360 B against approximately 34 GB physical RAM, with 5,661 MiB available. One sample reported approximately 51,813 page faults/s and zero page inputs/reads/outputs. Largest reported working sets included vmmemWSL, MemoryCompression, and chrome. These are post-run observations supplied by the coordinator, not measurements independently collected here. They cannot reconstruct b04/b05 pressure, prove a cleaner absent, or assign fault activity to the campaign. No unrelated application should be stopped on this evidence.

Microsoft defines a working set as the pageable virtual-memory pages currently resident in RAM. The memory manager can trim it; explicit API calls can also remove pages. Later access can restore pages through soft faults without disk I/O, or through hard faults requiring backing-store reads. Consequently, a fall followed by recovery need not mean allocation release followed by a leak. The interpretation that b04 was temporarily depressed and b05 refaulted pages is a hypothesis requiring correlated evidence. [Microsoft: Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set).

Use the counters precisely. `GetProcessMemoryInfo` with `PROCESS_MEMORY_COUNTERS_EX` reports current `WorkingSetSize` in bytes, lifetime `PeakWorkingSetSize`, cumulative `PageFaultCount`, and `PrivateUsage` as private commit charge. Fault count includes more than hard faults. Keep the official RSS calculation on current `WorkingSetSize`; neither peak working set nor private commit is a replacement baseline or exemption. Private commit is useful supplementary evidence about allocations. Check API success and native structure sizes instead of silently converting a failed query to zero. [GetProcessMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo), [PROCESS_MEMORY_COUNTERS_EX](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex).

`GetPerformanceInfo` supplies aggregate commit, commit limit, physical total, physical available, and page size. Most capacity fields are page counts and must be multiplied by `PageSize`. Physical available includes standby, free, and zero lists. Committing memory does not itself make every committed page resident; commit above physical RAM alone is therefore insufficient proof of current pressure. Capture a time series rather than infer conditions from one later snapshot. [GetPerformanceInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getperformanceinfo), [PERFORMANCE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information).

An external caller with the necessary process rights can invoke `EmptyWorkingSet`, which removes as many pages as possible from a specified process. This establishes a possible mechanism, not an identified culprit. A process-name search and current WPR status are useful limited checks; they do not rule out an exited utility, differently named service, application-initiated trim, or ordinary OS behavior. Attribution requires contemporaneous evidence such as the responsible utility's own timestamped log/configuration or an appropriately scoped diagnostic trace. [EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset).

Background execution, a minimized window, and low memory priority are separate states:

- Godot documents longer sleeps between frames when its editor is unfocused. Its current stable documentation describes a default unfocused limit of 10 FPS, and says continuous updating disables low-processor mode. This changes how often code/data are accessed; it is not a guarantee of Windows trimming. Read the actual pinned editor settings before applying these current documentation names. Do not enable continuous redraw just to keep pages hot. [Godot EditorSettings](https://docs.godotengine.org/en/stable/classes/class_editorsettings.html).
- On Windows 11, an occluded/minimized/non-visible, non-audible window-owning process may lose its requested high timer resolution. That is relevant to latency investigation, but the documentation does not say every minimize action empties the working set. `IsIconic` detects minimization; `IsWindowVisible` tests visibility style and can remain true when completely obscured. Record window state instead of inferring it from a screenshot or visibility flag alone. [SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation), [IsIconic](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-isiconic), [IsWindowVisible](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iswindowvisible).
- Memory priority 5 is normal/default. Lower-priority pages are preferred for trimming when other considerations are equal; this is a hint, not a residency guarantee. Query the owned processes' `ProcessMemoryPriority` and power-throttling state through `GetProcessInformation`. CPU priority class is a separate observation. [MEMORY_PRIORITY_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-memory_priority_information), [GetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocessinformation).
- Task Scheduler's documented default task priority is 7, mapped to below-normal process/thread priority; values 4–6 map to normal. Children can inherit an idle/below-normal parent class if creation does not explicitly override it. Inspect this campaign's task XML and actual child classes before concluding it uses that default. Task priority 7 is not proof that memory priority is below 5. [TaskSettings.Priority](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings-priority), [Scheduling Priorities](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities).

Proposed immediate diagnostic, for coordinator implementation and a separately captured actual exit:

1. Start exactly one fresh owned Python child under the existing bounded job wrapper; use a unique output path, a fixed total deadline of at most 120 seconds, and no engine. Identify the child by PID plus creation time. This is `STANDALONE_DIAGNOSTIC`, with no campaign PASS claim.
2. Record a pre-allocation sample, allocate one 32 MiB buffer, deliberately touch each page, and retain the same buffer. Record after-touch counters. Let the buffer remain untouched for a fixed idle interval, then touch the same pages again and record wake duration and counters. One or two predetermined cycles within the deadline suffice. Do not grow a list of samples or allocate another buffer each cycle; stream a small log. The synthetic touching belongs only in this probe, never in official warmup or measured batches.
3. Sample approximately once per second with UTC and monotonic timestamps: current working set, private commit, cumulative faults and deltas, system physical available/commit/limit, phase, PID identity, CPU priority and memory priority. Record configured working-set limits/flags once. API errors must be explicit. Polling itself keeps some code pages active, so absence of a drop is weak negative evidence.
4. A substantial idle working-set drop with roughly stable private commit, followed by recovery/fault growth on re-touch, supports residency churn in this probe. It does not distinguish OS trimming from an external caller, explain the complete editor workload, or prove that the campaign's host increase was harmless. A short negative result does not exclude a longer-period event.
5. Close the child normally and capture actual exit and owned-tree cleanup. Preserve all samples and the script/hash. Correlate results before deciding on a new engine run; do not repeatedly run probes until one happens to look favorable.

If readback finds an unintended owned-launch setting, the least invasive remedy is to correct that setting before any fresh warmup: ordinary normal CPU priority if the task was inadvertently background-class, or documented normal memory priority 5 if it was unexpectedly lowered. Record before/after readback and freeze the launch policy. These are conditional recommendations, not changes made here, and neither prevents ordinary trimming. Keep the owned editor's intended window state consistent and recorded; do not steal focus or force continuous redraw as a residency workaround.

If an external cleaner is positively identified, investigate whether it supports a narrowly scoped exclusion for the owned executable/process before proposing any change. No such cleaner or supported exclusion has been established. Do not disable a global service, empty standby memory, or close unrelated applications. If uncontrolled machine activity persists and no scoped correction exists, use a predeclared quiet period or a permitted isolated benchmark environment, preserving all failed attempts and the same workload/gates. Environment changes must be disclosed rather than retrospectively exempting S73.

Avoid purported fixes that manufacture a favorable RSS denominator: hard working-set floors, `VirtualLock`, `EmptyWorkingSet`, pre-touch padding, repeated warmups, higher replacement baselines, private/peak substitutions, or forced hot editor loops. Microsoft documents that a hard working-set minimum can prevent trimming below the requested size and warns that increased residency can deprive other processes of RAM; that is exactly why it is unsuitable as a neutral repair here. [SetProcessWorkingSetSizeEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-setprocessworkingsetsizeex).

Do not use WPR's Reference Set profile for this non-invasive probe or during the benchmark. Microsoft explicitly documents that starting it removes pages from the working sets of all processes, including the system, and can substantially affect performance. Other tracing requires a separately scoped overhead review; a reference-set metric would not replace the prescribed RSS metric. [Microsoft: Reference sets](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set).

After a justified, documented correction, a fresh campaign must still use the unchanged profile, five prescribed warmups, original baseline rule, complete required measurements, both timing gates, current-working-set growth check, frozen source/launcher identity, actual exits and cleanup. This research establishes a bounded way to collect missing evidence; it does not establish a valid benchmark result or guarantee the next campaign will pass.
