## Requirement and scope decision

I read the scoped AGENTS.md, current GT-02, section 2.2, TQ02, TX01/03/11/14/15/17.
GT-02 calls for a minimal typed client and mock operation fixture; engine
consumers belong to later gates. S46 now exposes an authenticated registered
`fixture.active-release` scope backed by actual protected NTFS creation and
atomic replacement, verified readback and durable custody. This addresses the
previous safe-write availability gap for that declared fixture scope. It is
more than a safe UNSUPPORTED answer or an in-memory mock.

This conclusion does not enable arbitrary-path writes. Global
`safe_open.safe_write` and `safe_open.atomic_replace` correctly stay false.
The fixed target is `active-release`; caller-controlled assets are bounded
inert JSON and logical references, not host paths or executable code. I found
no requirement in this GT-02 scope to advertise arbitrary filenames or a
Godot/Blender mutation consumer. Their absence is not waived or represented
as implemented.

## Security findings

No blocking finding remains in the reviewed closure.

- Registration is restricted to an exact live managed owner. It verifies the
  selector/consumer/storage ownership graph, protected native roots, Registry
  identity and event high-water. Discovery and later admission recheck the
  binding. Unregistered, detached and closed owners do not acquire public
  discovery authority. Stopped, pending, held and unreconciled readonly roots
  do not advertise new write availability.
- Protected writes use native handles, exact final path/FileID checks,
  reparse and link-count rejection, retained ancestors, protected owner DACLs,
  a writer guard and instance serialization. The replacement's expected file
  identity/hash, new bytes and changed FileID are checked; barriers precede
  acceptance. This relies on the documented trusted broker and confined
  worker boundary, not on rename flags being a conditional replace primitive
  in a directory an attacker may write.
- Work/control endpoints bind a retained process identity and validate its
  AppContainer primary token, package, user/session, low integrity and zero
  capabilities. Peer PID checks use the actual pipe connection. The service
  validates both roles and shared process identity before ownership transfer.
  Endpoint security excludes worker WRITE_DAC, WRITE_OWNER and second-instance
  creation. A bearer alone does not grant filesystem or Registry access.
- Credentials are minted locally and delivered through the verified work
  pipe bootstrap. They are absent from public discovery, command arguments
  and the native worker environment. Authentication precedes JSON parsing;
  roles, project and scopes are enforced at the host. Revoked sessions cannot
  signal Stop/Cancel. Issued bearer history survives rotation for redaction;
  secret-bearing input is rejected rather than silently changing its digest.
- Validation rejects malformed JSON, invalid graph/type/size fields, stale
  revision/deadline and unauthorized operations before intent publication.
  Typed output binds command IDs/project/schema and quarantine preserves
  UNKNOWN after ambiguous delivery. Inert asset/source text is neither
  evaluated nor accepted as authority to change root, process or model.
- I reran both deadline regressions: the independent watchdog revokes
  admission while a phase is blocked, and a late frame cannot dispatch after
  expiry before the watcher gets CPU. Failure keeps owned resources reachable
  for bounded drain/retry; work failure preserves healthy control. This review
  does not erase the earlier reproduced deadline failure.

## Limits retained

- Acceptance is for Windows local NTFS, a trusted broker, and its verified
  confined worker. Unrestricted same-account processes/administrators are
  not adversaries this boundary claims to contain.
- Three unavailable symlink-creation tests and one non-Windows capability
  test are explicitly skipped; Windows junction, hardlink, path-race and
  native denial tests execute. This does not certify Linux safe writes.
- The native typed-client integration substitutes peer verification; the
  separate compiled AppContainer client proves the peer/service boundary.
  Neither package is misrepresented as the other.
- Native owner reopen occurs in the same broker process. The full suite
  separately covers actual crash exit 87 and custody-only restart. Pending,
  stopped and verified-empty reopen roots remain held; no automatic recovery
  or power-loss durability claim is added.
- A synchronous native phase already admitted may finish after cancellation;
  further admission is held. The enclosing owned Job remains the final bound
  for a native call that cannot drain.
