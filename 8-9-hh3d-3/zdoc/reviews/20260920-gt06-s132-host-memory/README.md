# S132 host memory boundary diagnostic

Purpose: distinguish command-producer/journal/request-thread allocations from
native Godot, ACK waiting and offline assembly. This is a new question using the
unchanged S131 runtime53 closure; it does not repeat the coupled acceptance run.

`host_memory.py` executes at most seven stock HTTP batches of1000 commands each,
with the original command mix and client budgets. It launches no Godot or Blender.
Five warmups precede the original host-only RSS10%, handle and status2s screens.
The host subset cannot substitute for the complete campaign validator.

Supplementary snapshots before each batch, with its report alive, and after report
serialization while still held, then after report release record working set,
private commit, page faults, Python allocated blocks,
bounded recorder cardinality and system memory availability. No tracemalloc,
working-set trimming, priority changes or memory baseline adjustments are used.
The small accumulated metric rows and extra sampling are observation overhead;
no-growth would not establish no-leak or explain previous failures by itself.
The coupled RSS boundary is after native wait/read/parse and before assembly;
this host-only immediate post-GC boundary deliberately differs. A flat result
narrows only HTTP-only retention. Allocated-block count is not bytes/owners;
cumulative page faults do not prove working-set trimming by the OS.

Run ID `gt06-s129-host-memory-01` retains the existing passive supervisor namespace.
Runtime, helper, profile and binary hashes are pinned before dispatch. Output IDs
are exclusive and Stop is never erased. Child/outer budgets are1200/1230 seconds;
the passive observer and one-use task have separate bounded lifetimes.
Expected duration is8-18 minutes based on previous HTTP batches, subject to actual
durations; this is not an ETA for GT06 or the full tools plan.

Read actual retained target/helper exits, Job zero/closed, handles, source pins,
cleanup and all partial rows after terminal. Preserve first failure and repair only
derived metadata when raw evidence supports it. Diagnostic-only: no F13/F14,
accepted samples, final critic verdict, leak or root-cause claim.
