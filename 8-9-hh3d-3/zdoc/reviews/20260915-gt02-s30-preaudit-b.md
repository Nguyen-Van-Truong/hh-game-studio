## Findings, in priority order

### P1 — Inaccessible journal turns an already committed command into REJECTED

At the reviewed bytes, `studio/host/core/transport.py:51` classifies uncertainty
by a fixed code set. `_handle` at line 507 sends REJECTED for other
JournalError codes. `journal.py:260` applies the same guard/reload path to
lookup, archive and mutation methods, and `_load` at line 274 can itself raise
JOURNAL_FULL or JOURNAL_RECORD_LIMIT. Those failures do not establish that the
referenced command was rejected before applying.

The real-loopback repro below first completed a fixture.set command with
value=73, confirmed COMMITTED, and observed effect_count=1. It then caused each
failure using real private journal/guard files or configured read limits:

| Actual failure mechanism | Error code | lookup / same-ID submit / cancel / archive during failure |
|---|---|---|
| Another descriptor holds the real guard; lock timeout=25 ms | JOURNAL_LOCKED | All REJECTED, postconditions={} |
| Replace the private guard with a directory temporarily | JOURNAL_LOCK_FAILED | All REJECTED, postconditions={} |
| Add a second hardlink to the guard inside the disposable fixture | JOURNAL_LOCK_UNSAFE | All REJECTED, postconditions={} |
| Write a legacy lock marker containing `{}` | JOURNAL_LEGACY_LOCK_RECOVERY_REQUIRED | All REJECTED, postconditions={} |
| Reload with max_bytes below the existing journal size | JOURNAL_FULL | All REJECTED, postconditions={} |
| Reload with max_records=1 against the retained lease/pending/terminal journal | JOURNAL_RECORD_LIMIT | All REJECTED, postconditions={} |

Restoring each condition returned the original COMMITTED receipt, with the
same single effect. The repro does not fabricate JournalError exceptions or
replace transport dispatch. It demonstrates a status-contract violation, not
a duplicated effect: a caller sees a terminal rejection for an already
applied command and receives no uncertainty/reconcile postcondition.

Requirement: section 2.2 distinguishes pending/committed/unknown and requires
lookup before a retry after uncertainty; TQ02 requires same ID/hash to return
the same result and UNKNOWN after a write; TX11 forbids an unsupported ACK
claim when persistence/lookup cannot prove the outcome. This is a GT-02
acceptance blocker at the reviewed source hash.

Smallest sound classification change: preserve the failure phase. Mark
JournalError as outcome-unknown when acquiring the guard or reloading fails
before the journal operation can establish prior command state. Transport
should return UNKNOWN plus lookup/reconcile guidance for that flag, as well
as the existing uncertain codes. Keep capacity/validation rejection from a
successfully entered method distinguishable: a new command rejected by the
pre-admission reservation check can still be REJECTED. Do not blanket-map
every JOURNAL_FULL to UNKNOWN, and do not blanket-map it to REJECTED.

Also preserve uncertainty for guard-exit failures after a method/effect has
run; a before-method boolean must not accidentally label that later phase
as known no-effect. This is a design recommendation, not proof of a patch.
The coordinator must add positive UNKNOWN/readback assertions for these
routes and retain new-admission full/no-change regression coverage.

### Acceptance scope gap — Safe-open is truthfully unavailable

No general Windows safe-write capability was found or inferred.
`safe_open.py:154` returns safe_open=false, safe_write=false and
atomic_replace=false. Its root-probed instance at line 181 advertises only
read_identity; create_new/open_for_write/write_bytes/atomic_replace at
lines 236–246 raise UNSUPPORTED_SAFE_OPEN_WINDOWS before I/O. The legacy
boolean cannot unlock write through SafePathResolver. The live discovery
only exposes scoped fixture.inspect/fixture.set on fixture.counter; it does
not expose file mutation.

The focused tests executed actual Windows handle reads, junction/hardlink
rejection, ancestor/final-file swaps, root identity checks, no-effect mutation
rejection during junction swaps, and handle release. The exclusive-handle
hardlink counterexample still succeeds, justifying the disabled mutation
capability. This is evidence of truthful denial and a limited read probe.

The plan must retain both clauses: section 2.2 permits the explicit
UNSUPPORTED response when the safe primitive is unavailable, while TX15 says
“Safe-open unavailable là GAP.” Consequently, this bounded protocol fixture
may demonstrate the required denial behavior, but it has not demonstrated a
safe writer. An unqualified statement that all GT-02/TX15 requirements are
satisfied would hide an open requirement. Keep the availability GAP explicit
in coverage and acceptance scope; do not silently reclassify it as fulfilled
or enable GT-03/04 consumer mutation from this report. This report does not
change the plan or authorize dropping the requirement.

### P2 contract discrepancy — Dedicated open-lane code is absent

Section 2.2 names `UNSUPPORTED_OPEN_LANE`. No source declaration of that code
exists in the reviewed protocol/host closure. An independently constructed
valid raw-wire `open_lane.exec` request returned UNSUPPORTED_OPERATION,
as did python.eval, gdscript.eval, shell.exec, file.write and url.fetch.
None was advertised, and all left fixture state unchanged. Therefore the
security denial is proven; the literal specialized-code contract is not.
Resolve/document the dedicated capability-denial representation before
claiming exact coverage of that line. This is not an execution bypass.
