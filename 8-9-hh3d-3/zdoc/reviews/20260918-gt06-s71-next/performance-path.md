Scope: GT-06 S71, campaign `gt06-s71-campaign-01`, declared 49-file frozen closure `38a0848b68c4d6b34f1a03839008d54aa9e99a33458abaa88a939c8d2a744d86`, checkpoint `bb881a4a`. **Finding.** The growing journal is rescanned thousands of times per batch. The cache removes repeated JSON replay; it does not remove repeated history I/O and SHA-256. This is a source-proved linear-in-history operation that explains the shape of the slowdown. Its precise share of wall time remains unmeasured.

- `studio/tests/replay/benchmark_commands.py:36,94–109,268–305` selects `VerifiedJournal`, creates it once, and retains it for all 35 batches. Each batch submits 500 inspect, 300 validation-rejected, and 200 admitted commands. Inspect commands also persist pending and terminal receipts. There is no batch journal reset.
- `studio/host/core/journal.py:263–283,493,546,553–566` refreshes under the permanent kernel writer guard before every decorated operation, including lookup and lease checks. `lease_guard` also refreshes. This preserves cross-process dedupe/fencing decisions.
- `studio/host/replay/verified_journal.py:28–59,81–95` implements that refresh by opening the complete journal, reading it in 65,536-byte chunks, hashing every byte, checking identity/size/policy, and performing recovery fsync on a cache hit. It does this even after a known successful local append. `_append:97–120` extends the cached digest, but the next call still independently rereads all bytes to establish equality.
- `studio/host/replay/journal_index.py:16–121` packs offsets and gives expected constant-time command lookup. It does not scan all entries on each lookup. The full offset sum in `VerifiedJournal._load:74` runs on rebuild, not on a normal cache hit. Further index packing does not remove this hot path.

The successful, fresh-ID path in `studio/host/core/transport.py:589–658,706–809` gives this lower bound; each extra pending/connection-uncertain lookup adds another scan:

| Command class | Count/batch | Journal refreshes per command | New records |
| --- | ---: | ---: | ---: |
| Inspect | 500 | 4: existing lookup, pending append, terminal finish, terminal lookup | 1,000 |
| Admitted set | 200 | 6: the above plus admission lease check and effect lease guard | 400 |
| Invalid payload | 300 | 0: validation rejects before existing lookup | 0 |
| Auxiliary lease and successful cancel probe | 1 each | At least 7 combined | 3 |

Thus a complete batch adds **1,403 records and at least 3,207 full-history scans**, plus 1,403 append fsyncs. For batch ordinal b, history bytes grow approximately with b, so the repeated-read/hash work is approximately O(b) per fixed-size batch and O(B²) across B batches. Variable JSON number/ID lengths add small deviations. A new process run starts fresh; the growth is per run, not one journal accumulated across all ten runs. On a cache miss, the accepted complete parser and its recovery barrier add further work.

Three small joint artifacts in `.local/reviews/gt06-s71-campaign-01/run-00-attempt-01/` corroborate the timing shape: batches 00, 15, 29 span **56.228409 s, 167.188541 s, 308.716936 s**, all naming the frozen closure. These are combined host/native windows. They do not measure hash time, cache-miss count, disk versus OS-cache traffic, antivirus cost, or the native share. No multi-MB command/journal artifacts were read. The earlier `20260918-gt06-s71-growth/progress-01.json` estimate is a projection, not a completion promise.

**Optimization candidate with the smallest semantic change.** After this campaign, replace the allocating `stream.read` loop with a bounded reusable `bytearray`/`readinto`/`memoryview` hash loop, and evaluate a fixed larger buffer. Keep every byte in SHA-256, the same cap/overflow probe, regular-file/single-link checks, before/after fstat checks, identity/policy comparison, accepted-parser fallback, recovery fsync, append fsync, and cache invalidation on failure. Keep indexes, original receipt bytes, tombstones, limits, retry horizon, and writer ownership unchanged. This is a maintainable local implementation change with the same O(b) complexity; any speedup is speculative until measured. It cannot honestly promise to eliminate the overnight duration.

**Larger follow-on candidate.** A dedicated compound admission API could perform existing-ID reconciliation, admission validation, optional lease/revision validation, and pending append under one writer-guard interval and one initial full refresh. Preserve the existing standalone APIs, validation/error precedence, pre-ACK append fsync, pending-capacity reservation, and uncertainty handling; do not hold the guard across HTTP, engine work, sleeps, or terminal readback. The main mix would save 500 inspect refreshes plus 400 set refreshes: 900 of the minimum 3,200, approximately 28% of those scans, not 28% of total wall time. This requires changes to accepted core/transport and separate scope review; it is a design candidate, not a proven equivalent drop-in. External writers must still be reconciled at every new transaction boundary, including same-size/same-mtime corruption, and existing lease/effect boundaries must remain intact.

An O(1) metadata-only cache or tail-only reader would weaken the current contract: `test_verified_journal.py:49–58` deliberately mutates old bytes while preserving size/mtime. Under a mutable-file contract, an arbitrary earlier-byte change cannot be ruled out without reading those bytes or adding a separately proven mechanism that prevents/detects such changes. A hash chain, sidecar digest, or packed index alone does not establish that old disk bytes stayed unchanged. Avoid journal clearing, receipt eviction, dropping tombstones, skipped fsyncs, shortened batches, or parallel native runs as speed fixes.

**Timing of change.** This optimization can wait. The static finding is a performance cost, not proof of broken durability or duplicate/lost effects. Keep the healthy frozen campaign untouched, with its existing deadlines and gates. If it completes, retain its evidence for that exact source. An optimized source needs a new closure, adversarial journal regression checks (external append/replace/truncate/same-metadata corruption, fsync failure/reopen, concurrent writers, dedupe/archive/tombstones), and its own unchanged full benchmark profile; old samples and signatures cannot be transferred or mixed. If the present campaign becomes terminal/fails, preserve that outcome before considering a fresh optimized run. No current result is invalidated merely by writing this report.
