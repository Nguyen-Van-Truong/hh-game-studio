# S77 derived SQLite journal index design

2026-09-18, Asia/Saigon. Design only; AUTHORITY=0. No implementation, tests, engine launch, evidence scan, acceptance verdict or plan change. Read the local AGENTS.md, S77 tools-plan top, host-retention-review.md, the index/cache implementation and immediate callers/tests. `journal_cache.py` does not exist here: its intended subject is `host/replay/verified_journal.py`. HEAD observed: `398de65ca4f98cede6646df4b5f1809c4e28de5b`.

**Recommendation:** give each `VerifiedJournal` one private, disposable SQLite database containing every command identity and record offset. Keep the checksummed JSONL journal, accepted validation, OS guard, append/fsync and compaction implementation authoritative. Rebuild the database from that journal on every new instance and whenever verified history changes. Never reload an old SQLite file as trusted command history. This removes the growing Python command dictionary and offset array identified in host-retention-review.md; it does not establish an RSS or latency PASS.

## Storage and compatibility

Add a small `DiskJournalIndex` owner in `host/replay/disk_journal_index.py`; expose offset and command views to the existing Journal. Keep old `PackedOffsets`/`ProjectCommandIndex` available for their historical tests and reference behavior; do not turn them into hidden file owners. No hash-only identity, Bloom-filter decision, prefix-specific grammar, eviction, truncated ID or removed tombstone. Narrow scope agreed with coordinator: existing pending/lease containers stay unchanged. Pending admission is limited by policy; during replay, total pending/lease cardinality is bounded by the accepted record cap. Distinct lease targets can still grow toward that cap, so this proposal removes the campaign's command/offset retention, not all possible Journal key growth.

Agreed integration API: `DiskJournalIndex(private_parent: Path, *, cache_kib=256, cached_statements=32)`, `.commands` as `MutableMapping[(str,str), int]`, `.offsets` as `Sequence[(uint64,uint64)]` with `append/clear`, `transaction()` context manager, idempotent `close()`, and `DiskIndexError` with a stable code and private exception cause. Constructor/close errors carry `cleanup_owner` whenever a connection/path still needs release; VerifiedJournal adopts that owner for retry. One owner contains the connection and both views. Each standalone view mutation is atomic; when an owner transaction is active it joins that transaction. The caller groups command/offset writes under one context. A module-local mutex serializes its SQLite access; the root integration additionally serializes the complete journal operation, fingerprint and pending/lease state. The root owns `verified_journal.py` integration; no source work starts before the coordinator's explicit native-terminal signal.

Suggested schema (all names/SQL static; values bound with placeholders):

| Table | Key and stored fields | Purpose |
|---|---|---|
| `meta` | one row: schema version, generation, record/command counts, next ordinals | Constant-size transactional bookkeeping. Live verification fingerprint remains on the Journal owner. |
| `records` | `record_no INTEGER PRIMARY KEY`; `offset_u64 BLOB`, `length_u64 BLOB` | Every historical record, including lease/pending/terminal rows. Offsets and lengths are exactly eight unsigned big-endian bytes, preserving the full current uint64 helper domain. |
| `projects` | `project_order INTEGER PRIMARY KEY`; `project_key BLOB NOT NULL UNIQUE`; next command ordinal | First surviving project insertion order. No Python project cache. |
| `commands` | composite primary key `(project_order, command_key BLOB)`; `command_order INTEGER`; `latest_record BLOB`; unique index `(project_order, command_order)` | Exact command lookup and grouped iteration. Use `WITHOUT ROWID`; explicit BLOB type/length checks. |

`latest_record` uses canonical unsigned big-endian bytes, at least one byte, decoded to Python `int` on access. This preserves the current helper's nonnegative Python-integer domain, including its `2**70` test; SQLite's signed integer range must not silently narrow it. Actual record numbers/ordinals fit the configured record cap. Before SQLite binding, validate that ordinal allocation fits signed 64 bits; unexpected exhaustion is an index failure, never wraparound. Append offset validation remains atomic and rejects bool, negative and out-of-range values before touching either column.

Encode **each key component separately** as `value.encode('utf-8', 'surrogatepass')`, and decode with the inverse. Bind as bytes/BLOB, never TEXT; never concatenate with a separator, normalize Unicode, case-fold or stringify the tuple. NUL, empty helper keys, composed/decomposed Unicode, separators, supplementary characters and lone surrogates remain distinct. In particular `U+10000` must differ from the Python string containing `U+D800,U+DC00`; UTF-16 with surrogate passing would collapse that pair and is unsuitable. Python documents surrogate handling and SQLite compares BLOB values bytewise. [Python codecs](https://docs.python.org/3.11/library/codecs.html#error-handlers), [SQLite storage classes/comparison](https://www.sqlite.org/datatype3.html#comparison_expressions).

This is container compatibility, not expanded wire acceptance: current `core/limits.py` rejects lone surrogates in canonical journal records, and Journal rejects empty command/project IDs. Those restrictions remain where they are. Type/error contracts stay equivalent for ordinary string tuples, missing keys, integer positions/negative indexes and mapping values. Document the journal's plain-string boundary rather than promising arbitrary adversarial str-subclass equality semantics.

Iteration must explicitly reproduce the existing **project insertion order, then command insertion order within that project**, not flat global insertion or lexicographic BLOB order. Updating a latest record leaves its ordinal unchanged. Deleting the last command removes its project; reinsertion receives a new project ordinal. Deleting/reinserting a command moves it to the end within its surviving project. Every SELECT uses the appropriate `ORDER BY`; SQLite provides no implicit row-order guarantee. [SQLite SELECT ordering](https://www.sqlite.org/lang_select.html#the_order_by_clause).

Implement point lookups and streaming views, including an efficient `values()` used by compaction; no `fetchall`, `dict(items())`, all-key list, offset array or full decoded-history shadow. Values/keys views refer to the stable owner, not a connection generation, so a newly iterated view sees clear/rebuild. A live iterator checks generation and fails if mutated/rebuilt. Keep iterators internal to the Journal lock; close cursors in `finally`, including early exit. Covering order indexes or nested ordered project/command scans avoid a cardinality-sized sorter. Slice compatibility can materialize an explicitly requested result, as today's helper does, but production paths must never request a whole slice; returned data is not a retained cache.

## Durability and failure protocol

Owner states: `BUILDING`, `VALID`, `POISONED`, `CLOSED`; readers cannot observe BUILDING/POISONED state. Initialize the local mutex and owner before `Journal.__init__` invokes the subclass `_load`. Install empty disk views **before** accepted replay starts; converting a fully populated dict/list afterward defeats the memory objective.

1. **Open/rebuild:** under the existing authoritative writer guard, retire the old store, create a new private database, and call accepted `Journal._load()` with the disk views installed. It still parses each bounded line, checks SHA-256 and history, applies limits, and performs the recovery fsync. Stream into SQLite in small transactions (at most 256 records); they are internal BUILDING state, never acknowledged or reusable across restart. The parser's prior-record lookups work against the candidate. A rebuild failure poisons the whole candidate, including pending/leases, even if an earlier chunk committed.
2. **Publish rebuilt state:** preserve the existing SHA-512 exact-byte snapshot/policy/identity checks and compare streamed offset-length sum with observed size. Compare snapshots bracketing rebuild as well, rejecting a change during the rebuild window. Set VALID/fingerprint only after accepted recovery fsync and all SQLite commits succeed. Empty/missing journal follows the accepted empty-history behavior. Do not replace the full-history check with mtime, length, last-record checksum or a persisted SQLite “valid” bit.
3. **Local append:** after locked reload verification, start one SQLite transaction, invalidate the live fingerprint, then call accepted `Journal._append(record)`. Its validation, capacity reservation, exact serializer, file append and fsync remain in their original order. The subsequent command view mutation and offset append update the same SQLite transaction. Existing `_pending`/`_leases` changes remain in memory: rollback must poison them too, not pretend they rolled back with SQLite. Commit SQLite only after the accepted append returns. Then extend the digest from the exact encoded journal line using the existing identity/size checks. No database row may authorize a receipt before the JSONL durability barrier.
4. **Post-fsync failure:** if command update, pending/lease update, offset insert or SQLite commit fails after the JSONL append, roll back the SQLite transaction if possible, clear the verified fingerprint and latch POISONED. Raise a stable `JournalError('JOURNAL_INDEX_UNAVAILABLE')` with **`outcome_unknown=True`**. No COMMITTED/no-effect/COMMAND_NOT_FOUND result, fresh ID or immediate retry execution. Existing `LoopbackFixtureHost._journal_failure` converts that local flag to UNKNOWN/503 and stops work admission; preserve lookup/reconciliation access. The original durable record is never truncated or compensated because a cache write failed.
5. **Next operation:** acquire the same locks, discard the poisoned store and perform a complete accepted replay/recovery fsync before any lookup, lease decision or new append. It may recover the original pending/terminal receipt and dedupe it; if rebuilding fails, remain unavailable/UNKNOWN. Never fall back to an empty or partially built index. Fresh process recovery also rebuilds; an in-memory poison flag alone is insufficient.

Wrap SQLite exceptions at the store boundary; never expose raw SQL, keys or local paths. Treat ambiguous commit/rollback/close outcomes conservatively. The base `_mutating` decorator marks failures before entering or after returning the method as unknown, but **does not automatically mark mid-method cache failures**; the adapter must set the flag itself. Preserve existing, proven pre-admission validation/capacity rejections and their codes. Unexpected cache failures may conservatively return UNKNOWN even before append; they must not masquerade as JOURNAL_FULL. Journal write/fsync failures continue through the accepted uncertain path. Do not swallow `BaseException`: invalidate state on every interrupted mutation, attempt bounded cleanup, and re-raise interruption with original semantics.

There is no atomic transaction spanning SQLite and JSONL, and none is needed: the latter wins every crash window. SQLite rollback is still useful for consistent in-process views; use actual transactions with rollback journaling, not `journal_mode=OFF`. SQLite documents that failures can roll back a statement or an entire transaction, so cleanup must check transaction state and never assume which survived. [SQLite transactions](https://www.sqlite.org/lang_transaction.html).

**External writers and compaction:** every public operation retains the existing OS guard and exact-history read/fsync. External append, truncation, same-size/same-mtime edits, replacement even with identical bytes, or policy changes force accepted replay; malformed tails/checksums remain errors. Compaction continues to stream every latest command/tombstone and lease through the accepted temp-file/fsync/replace path. After replace, force a new index generation; all offsets change. If post-replace rebuilding fails, the compacted journal remains authoritative and the response is UNKNOWN. These guarantees assume cooperating writers and the existing private-namespace boundary, not protection from an unrestricted same-principal process racing arbitrary file writes.

## Memory, disk security and lifetime

Start with one connection, `isolation_level=None`, `check_same_thread=False`, `cached_statements=32`, no custom row factory, no extensions. Use explicit BEGIN/COMMIT/ROLLBACK and bound every value. Check the deployed SQLite version/threading mode rather than inferring it from Python 3.11. Serialize all connection/cursor operations, verification, mutation and close with one per-instance mutex held outside the existing OS guard. The connection crosses HTTP/worker/Stop threads, so creator-thread default is inappropriate. No concurrent use of a connection and no per-thread connection pool. The existing non-reentrant `lease_guard` rule still applies; a local RLock does not permit recursively taking the OS guard. Explicitly close connections: a Python sqlite connection context manager does not close them. [Python sqlite3](https://docs.python.org/3.11/library/sqlite3.html), [SQLite threading](https://www.sqlite.org/threadsafe.html).

Initial fixed settings, applied/read back before ingest: `page_size=4096`, `cache_size=-256`, `mmap_size=0`, `cache_spill=ON`, `journal_mode=DELETE`, `synchronous=FULL`, `temp_store=FILE`; no WAL, ATTACH, VACUUM, TEMP tables or ad hoc sort queries. Keep single-row SQL mutations and indexed iteration; no batch-sized SQL parameter list. Set a finite database page budget from the existing journal byte/record caps with conservative measured overhead, not command count observed so far. Hitting it is index unavailability, never permission to remove IDs. SQLite's page cache is a suggested cache limit, not a total allocation/RSS ceiling; spilling permits large transactions to write dirty pages, and zero mmap disables mapped I/O. These settings require live readback. [SQLite PRAGMA reference](https://www.sqlite.org/pragma.html).

No additional Python LRU is initially necessary; receipts still decode from authoritative JSONL on demand. The new module retains only scalar counts, fixed statement cache and current cursor/row; VerifiedJournal retains its fingerprint/fixed hash buffer and unchanged pending/lease maps. Disk grows with complete command/record history. SQLite has allocator/B-tree/rollback bookkeeping outside its page cache, so prove a stable measured plateau and no cardinality-sized SQL sorter; do not label `cache_size` a hard process-memory proof. A later optional LRU must have both entry and byte caps, be generation-bound, and never answer a miss without exact disk lookup. Do not use process-global hard/soft heap changes or forced cache/working-set trimming to satisfy the benchmark.

Create a cryptographically unpredictable directory under the trusted private host state root, using `mkdtemp(dir=<absolute private root>)`; never accept a request-supplied index path or fall back to shared TEMP. Apply the existing namespace/reparse/hardlink checks and required Windows private ACL policy to the directory/database; POSIX mode alone is not a Windows ACL proof. Verify regular single-link database files and allowed parents. Each Journal instance has its own store: no process shares SQLite paths; instances coordinate solely through the authoritative journal guard. Directory creation must succeed securely before use. [Python tempfile](https://docs.python.org/3.11/library/tempfile.html#tempfile.mkdtemp).

The database contains complete identifiers, so it is private state despite omitting receipt bodies. Rollback journals normally sit beside the database; other SQLite temporary files can use other locations. Avoid statements that need transient sort/materialization or multi-row statement journals, and verify those query plans/actual file locations on the pinned build. If any such spill remains, require the existing private per-process temporary environment before launch; do not change global SQLite temp-directory state from a worker thread. Files are not evidence, source, publications or logs; keep them out of manifests/commits. Neither deletion nor secure-delete implies forensic erasure. [SQLite temporary files](https://www.sqlite.org/tempfiles.html).

Add idempotent `VerifiedJournal.close()` and context-manager support. It prevents new operations, waits for the current mutex owner, closes cursors/connection, then removes only the exact owned private files/directory after containment and identity checks. Call it only after producers/HTTP handlers/Stop persistence threads have drained. On close/unlink failure retain a retryable cleanup owner and report cleanup held; never claim no leftovers or recursively delete an unverified path. Constructor failures must run the same cleanup. Avoid relying on `__del__`. Crash leftovers are never reopened; reclaim them only by a separate ownership-verified cleanup, not a startup wildcard sweep. Do not accumulate failed generations or connections on repeated rebuild failure.
