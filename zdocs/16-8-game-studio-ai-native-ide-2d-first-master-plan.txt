0.3 LUẬT BẤT BIẾN (INVARIANTS) — vi phạm là reject PR

  I1 (SỬA v2). 100% mutation vào AUTHORITATIVE PROJECT MODEL đi qua typed
      CommandDispatcher (một cửa duy nhất, cả UI người lẫn bus agent lẫn
      ingest hệ thống). Nút UI mutating = phát command. View-state thuần UI
      (pan/zoom viewport, tab, filter, selection cục bộ) KHÔNG bắt buộc qua
      bus. Không tồn tại đường ghi document nào khác: worker ghi staging chứ
      không ghi project; file sửa ngoài (VS Code) được ingest thành synthetic
      command; không có "sửa tay JSON rồi editor tự nuốt im lặng".
  I2 (SỬA v2). Mọi command mutating: validate -> ghi WAL record (full
      command + inverse, checksum) -> FLUSH -> áp vào document -> rồi mới ACK
      thành công. Có inverse hoặc nằm trong transaction có inverse. Phát
      event tương ứng sau commit.
  I3. Play luôn là PROCESS RIÊNG chạy từ SNAPSHOT BẤT BIẾN. Editor không bao
      giờ load gameplay code (Luau) vào process của nó.
  I4 (SỬA v2). Luau: sandbox(true) + memory limit + interrupt deadline luôn
      bật; CHỈ compile từ source (cấm nạp bytecode từ ngoài); mutation từ
      gs.* buffer per-callback, commit khi callback kết thúc thành công;
      host function bounded, không blocking.
  I5. Scene/asset meta là JSON canonical (5.4b), schema_version bắt buộc,
      unknown field ở MỌI cấp nesting: giữ nguyên round-trip, không drop.
  I6. Mọi write file: tmp + rename. WAL/registry: append-only, mỗi record có
      seq + checksum; đọc gặp record hỏng ở ĐUÔI: cắt tại đó (truncated-tail
      tolerated); hỏng ở GIỮA: dừng + báo, không đoán.
  I7 (SỬA v2.1). Mọi path GHI và mọi path tham chiếu trong project (dest_rel,
      scene path, script path...): canonicalize, phải nằm dưới project root;
      từ chối symlink thoát root, tên Windows reserved (CON, NUL, COM1..),
      path >200 ký tự. NGOẠI LỆ DUY NHẤT: nguồn ĐỌC của asset.import
      (src_abs) và build.game out_dir được phép ngoài root — src_abs vẫn
      phải là file thường (không device/UNC lạ), qua sniffing + caps 8.1;
      out_dir không được nằm TRONG project root (tránh export đệ quy).
  I8 (SỬA v2). Bus chỉ bind 127.0.0.1 + token. Danh tính (actor_id) do
      SERVER CẤP sau handshake — không tin bất kỳ trường danh tính nào client
      tự khai trên từng request. Token/secret không vào log/event/journal.
  I9 (LÀM RÕ v2.1). Không thêm NGÔN NGỮ/FRAMEWORK lớn ngoài bảng 2.1.
      Utility crate Rust nhỏ (serde/serde_json, ulid, crc32fast, image,

1.2 ĐÓNG GÓI (trả lời "IDE / tool / engine / app?")
  - SẢN PHẨM = 1 APP desktop: gs-editor.exe.
  - ENGINE = các crate Rust bên trong repo — chi tiết triển khai, KHÔNG
    phát hành engine rời (tránh bẫy "làm engine 10 năm").
  - PLAYER = gs-player.exe đi kèm (Play trong dev; đóng gói cùng assets
    thành game khi export).

2.4 PLAY = PROCESS RIÊNG TỪ SNAPSHOT BẤT BIẾN (C2)
  Godot chạy game process riêng (kể cả khi cửa sổ được nhúng vào editor từ
  4.4) — editor không chết theo game, không cần domain reload kiểu Unity.

      .gs/runtime/play/<play_id>/

        project-settings.json

2.8 UNDO ĐA TÁC NHÂN (C5 — viết lại)
  - Mỗi transaction commit = 1 entry {txn_id, seq, actor_id, label,
    commands[], inverses[], base_revision, new_revision}.
  - MỘT lịch sử chung cho document (như Google Docs), entry gắn actor.
  - Con người (UI): Ctrl+Z = undo entry MỚI NHẤT của lịch sử (quyền tối
    thượng — người luôn undo được mọi thứ, kể cả việc agent làm).
  - Agent (mặc định): undo.revert_own {txn_id} — chỉ revert transaction
    CỦA CHÍNH NÓ, và chỉ khi không có transaction sau đó đụng cùng
    entity/field (không conflict). Muốn revert của người/actor khác: cần
    capability "undo.others".
  - SELECTIVE UNDO (revert entry không phải mới nhất): KHÔNG áp inverse mù.
    Tạo TRANSACTION MỚI từ inverse cũ + precondition (giá trị hiện tại
    phải bằng giá trị sau-transaction-cũ trên từng field đụng tới); lệch
    -> E_CONFLICT kèm diff, actor tự quyết ghi đè bằng lệnh thường.
  - Stack cap 500 entry / 64MB inverse; tràn bỏ đầu cũ (đã autosave nên
    không mất an toàn dữ liệu).
  - Batch/gizmo-drag của người auto-gộp thành 1 transaction khi thả chuột.

4.0 EXECUTABLE REGISTRY (C3 — thay "bảng trong docs" của v1)
  Nguồn chân lý là CODE: crates/gs-registry khai báo từng method:
    method "entity.spawn" {
      input: JsonSchema, output: JsonSchema,
      side_effect: Mutating | ReadOnly | Job,
      undo: Auto | None | Special("..."),
      capability: Base | Destructive("entity.destroy.mass") | UiOnly,
      idempotency: ByCommandId | Natural | NotApplicable,
      timeout_ms, cancellable: bool,
      errors: [APP_CODE...], emits: [event...]
    }
  Từ registry SINH: docs/PROTOCOL.md, validator server, help CLI, tool list
  MCP, conformance test (gọi từng method với input hợp lệ/không hợp lệ sinh
  từ schema — chạy trong CI). Bảng 4.2 dưới đây là BẢN CHIẾU để người đọc
  plan; số lượng chính xác do registry quyết — không quảng cáo "84 lệnh"
  bằng đếm tay nữa (v1 đếm sai).

4.1 ENVELOPE & FRAMING (JSON-RPC 2.0 tuân thủ — C3)
  - Transport: TCP 127.0.0.1. NDJSON: mỗi thông điệp 1 dòng UTF-8 kết thúc
    LF; DÒNG TỐI ĐA 4MB (sửa v2.1/C16 — phải chứa được script.set_source
    256KB sau escape, transaction 200 lệnh, tilemap patch ~1MB; 256KB của
    v2 tự mâu thuẫn); đọc quá cap -> trả -32600/E_PROTO rồi ĐÓNG kết nối
    (GS-EC-58); parse sau khi đọc đủ dòng; partial read được buffer; idle
    timeout 120s có ping (session.ping); chống slowloris: >10s không hoàn
    thành 1 dòng -> đóng. Payload lớn hơn nữa đi đường FILE (scene.dump,
    artifact.get trả path — không nhét blob vào response).
  - Request:
    {"jsonrpc":"2.0","id":"a-000123","method":"entity.spawn",
     "params":{"scene_id":"s_main","command_id":"01J...ULID","...":"..."}}
    Sau handshake, MỌI danh tính lấy từ connection — không có meta.actor
    client tự khai (C4). dry_run/live/confirmation_id là field trong params
    (thuộc schema từng method), không phải meta tự do.
  - Response kết quả: {"jsonrpc":"2.0","id":"a-000123","result":{...,
    "revision":"r-000451","txn_id":"t-000318"}}
  - Response lỗi (SPEC: code là SỐ):
    {"jsonrpc":"2.0","id":"a-000123","error":{"code":-32602,
     "message":"invalid params","data":{"app_code":"E_VALIDATION",
     "field":"x","reason":"nan","retryable":false}}}
    Mã số: -32700 parse; -32600 invalid request; -32601 method not found;
    -32602 invalid params; -32000 app error (mọi app_code nghiệp vụ);
    -32001 unauthorized; -32002 conflict; -32003 busy/budget.
  - Event = NOTIFICATION chuẩn (không id):
    {"jsonrpc":"2.0","method":"event.scene_changed","params":{"seq":4512,
     "actor_id":"act_02","txn_id":"t-000318","summary":"entity.spawn
     crate_1","entities":["e_000042"],"revision":"r-000451"}}
  - JSON-RPC ARRAY BATCH: KHÔNG hỗ trợ (server trả -32600) — spec cho phép
    xử lý song song/không thứ tự, trái nhu cầu atomicity; dùng
    transaction.execute. Công bố rõ trong hello.

4.2 BẢN CHIẾU METHOD v1 (registry là chân lý; U=undo auto, D=cần
    capability/confirm, P=cần player, UI=chỉ dispatcher in-process của UI)

4.3 IDEMPOTENCY & OPTIMISTIC CONCURRENCY (C5)
  - command_id: ULID client sinh, bắt buộc với MỌI lệnh mutating + Job.
    Server giữ dedup map (command_id -> txn_id/result) WAL-backed, cửa sổ
    24h / 100k entry LRU (v2.1/C18 — 10k quá hẹp: agent chạm budget
    200 lệnh/phút sẽ evict trong ~1 giờ). Khi mở project: dedup dựng lại
    bằng cách quét TOÀN BỘ WAL còn giữ (cả 10 file xoay vòng), KHÔNG chỉ
    đoạn replay sau autosave — retry một lệnh đã commit trước snapshot
    vẫn phải trả kết quả cũ (GS-EC-57). Retry cùng command_id -> trả lại
    KẾT QUẢ CŨ, không áp lại (TCP rớt sau commit trước response an toàn).
  - revision: document revision "r-xxxxxx" tăng mỗi txn commit. Lệnh
    mutating nhận expected_revision (tùy chọn nhưng agent NÊN gửi — ghi
    trong AGENTS.md); lệch -> -32002/E_CONFLICT kèm current_revision +
    diff tóm tắt các entity đụng độ. Đọc (component.get/scene.stats) trả
    revision hiện tại để client bám.
  - Lock: entity.lock trả owner_token, TTL 60s, renew bằng gọi lại; quota
    100 lock/actor; disconnect -> release; NGƯỜI (UI) có quyền force-unlock
    mọi lock (người > agent); lệnh đụng entity khóa bởi actor khác ->
    E_LOCKED kèm owner + note.

4.4 AUTHORITY MODEL (C4 — server cấp danh tính, không tin client)
  - Handshake: client gửi token (đọc từ endpoint.json — quyền đọc file =
    quyền nối bus). Server cấp actor_id ("act_NN") + principal:
      * "human_ui": CHỈ dispatcher in-process của cửa sổ editor — không
        cấp qua TCP bao giờ (UI không đi TCP; nó gọi thẳng dispatcher).
      * "agent": mọi kết nối TCP. client_name chỉ là nhãn hiển thị,
        không phải quyền.
    => agent KHÔNG THỂ giả human:ui, không thể tự pause/resume actor khác,
    không thể tự approve confirmation (các method [UI] bị từ chối
    -32001 cho principal agent).
  - Capability: server + UI người cấp (capability.grant), có scope (method
    cụ thể hoặc nhóm), expiry, max_use, audit vào WAL. Mặc định agent: mọi
    lệnh không-D + play/obs/judge theo budget.
  - Pause (I12): actor bị pause chỉ được pure-read (component.get, obs.*
    đọc, session.*); play/input/build/gen_image/undo/txn mới -> E_PAUSED;
    job đang bay của actor đó bị hủy an toàn (job cancel, build cancel);
    resume chỉ từ UI.
  - Rà soát bảng 4.2 theo nguyên tắc: mọi method có side effect người-thấy
    -được đều phải gắn capability class trong registry — conformance test
    kiểm principal agent gọi method [UI] phải bị chặn.

4.5 CONFIRMATION (C4)
  Lệnh D thiếu capability -> server phát EVENT confirmation.request
  {confirmation_id, actor_id, method, params_canonical_hash,
  base_revision, summary, expires_in:120s} -> UI hiện hộp thoại (9.7).
  Người approve/deny (chỉ UI). Approve -> server thực thi NGAY command đã
  giữ (không cần agent gửi lại — tránh TOCTOU); confirmation_id dùng MỘT
  lần, bind đủ actor + hash + revision; đổi params/revision -> vô hiệu.
  TXN CHỨA LỆNH D (v2.1/C20): transaction.execute phân loại theo lệnh
  nguy hiểm nhất bên trong, đánh giá TRƯỚC KHI chạy — một confirmation
  cho cả txn (summary liệt kê các lệnh D); approve thì txn chạy atomic
  như thường, không confirm từng lệnh con.
  CHỐNG SALAMI (viết rõ v2.1): lệnh cùng loại với size >=80% ngưỡng D
  (ví dụ destroy 16-19 entity khi ngưỡng D là >20) lặp >3 lần/phút cùng
  actor -> từ lần kế tiếp nâng thành D + ghi log heuristic rõ ràng.

4.6 BUDGET (số là mục tiêu I13)
  mutating 200 LỆNH/phút/actor — transaction.execute đếm theo SỐ LỆNH

5.4b CANONICAL WRITER SPEC (C9 — "sorted keys" đơn thuần chưa đủ)
  - Key sort: bytewise UTF-8, ĐỆ QUY mọi object (tham khảo tinh thần
    RFC 8785/JCS, không cần tuân thủ từng bit).
  - entities sort theo id tăng dần THEO GIÁ TRỊ SỐ u64 sau tiền tố
    (v2.1/C19 — bytewise sai khi id vượt bề rộng pad); trong components
    sort theo tên bytewise (tên component là ASCII cố định).
  - Float: serialize shortest round-trip (Rust ryu); -0.0 chuẩn hóa thành
    0.0 TRƯỚC khi ghi; cấm NaN/Inf (validator chặn từ cửa — I5).
  - Indent 2 space, LF, UTF-8 không BOM, newline cuối file.
  - Unknown field: mỗi component/entity giữ map "x-unknown" nội bộ khi
    parse, ghi lại nguyên văn đúng vị trí khi save (test round-trip mọi
    cấp nesting trong CI).
  - Mục tiêu: cùng document -> cùng bytes (diff/merge/hash ổn định).

5.5 WAL & RECOVERY (C1 — viết lại toàn bộ; v1 "digest" là lỗi P0)
  - File: .gs/wal/<ts>.wal.jsonl, append-only, xoay 64MB giữ 10 file.
  - RECORD THẬT SỰ REPLAY ĐƯỢC:
      {"seq":4512,"kind":"txn",
       "txn_id":"t-000318","command_id":"01J...","actor_id":"act_02",
       "base_revision":"r-000450","new_revision":"r-000451",
       "commands":[{"method":"entity.spawn","params":{...FULL normalized,
         đã validate, id đã cấp...}}],
       "inverses":[{"method":"entity.destroy","params":{...}}],
       "schema_version":1,"ts":"...","crc32":"..."}
    Payload quá 1MB (hiếm — tilemap lớn): body ghi ra .gs/wal/blobs/
    <sha256> (CAS bền vững), record giữ {$blob:"sha256:..."} — blob GC
    CHỈ khi không còn WAL/undo entry nào tham chiếu.
  - Một txn = MỘT record nguyên tử (không begin/commit hai dòng — đơn
    giản và đủ vì dispatcher single-writer). Ghi record -> flush (fsync
    theo policy: mặc định fdatasync mỗi record; config "relaxed" fsync
    100ms/lần cho máy chậm, ghi rõ trade-off) -> áp document -> ACK (I2).
  - Snapshot (autosave): .gs/autosave/<scene>.<ts>.json + sidecar
    {"last_committed_seq":4500,"revision":"r-000450","doc_sha256":"..."}
    mỗi 60s hoặc 50 txn, và LUÔN trước play.start; giữ 20 bản.
  - DIRTY MARKER (định nghĩa v2.1): editor ghi .gs/dirty (file rỗng) khi
    có txn commit chưa nằm trong save/autosave mới nhất; xóa khi save_all
    thành công + khi shutdown sạch. Mở project thấy .gs/dirty -> chạy
    recovery; không thấy -> mở thường (WAL vẫn được quét cho dedup).
  - RECOVERY khi mở project có marker dirty:
      1) nạp autosave mới nhất có sidecar hợp lệ (verify doc_sha256);
      2) replay WAL các record seq > last_committed_seq, verify crc32

7.5 VÍ DỤ door.luau (INLINE v2.1/C15 — khớp props trong sample 5.4;
  bản chạy được nằm ở templates/; state để trong self.state cho persist
  qua hot reload — 7.4)

    --!strict
    local M = {}

    function M.on_init(self)
      -- self.props từ Script component (5.4): locked, key_tag, open_sprite
      if self.state.locked == nil then
        self.state.locked = self.props.locked
      end
    end

    function M.on_event(self, name, data)
      if name ~= "collision_enter" then return end
      if not self.state.locked then return end
      -- key_pickup.luau đã gs.add_tag(player, self.props.key_tag)
      if gs.has_tag(data.other, "player")
         and gs.has_tag(data.other, self.props.key_tag) then
        self.state.locked = false
        gs.set_sprite(self.id, self.props.open_sprite)
        gs.set_component(self.id, "Collider2D", { is_sensor = true })
        gs.emit("DoorOpened", { door = self.id, by = data.other })
      end
    end

    return M

  (Mọi gs.* mutating ở trên vào buffer, commit khi on_event return —
   nếu giữa chừng vượt deadline thì cửa KHÔNG mở nửa vời.)
